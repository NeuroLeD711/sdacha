## Обзор системы

**Фриланс-Эскроу** — кроссплатформенная система для предоставления и исполнения фриланс-услуг с интегрированным модулем условного депонирования (Escrow).

### Ключевые возможности
- Публикация проектов заказчиками
- Ставки от исполнителей
- Условное депонирование средств
- Чат в реальном времени
- Система отзывов и рейтингов
- Автоматический контроль сроков
- Разрешение споров

## Акторы

### 1. Гость (Guest)
- Просмотр списка проектов
- Регистрация в системе

### 2. Заказчик (Customer)
- Создание проектов
- Принятие ставок
- Пополнение баланса
- Оплата проектов (депонирование)
- Приём/отклонение результатов
- Открытие споров
- Оставление отзывов

### 3. Исполнитель (Contractor)
- Просмотр проектов
- Размещение ставок
- Выполнение работ
- Сдача работ
- Открытие споров
- Оставление отзывов

### 4. Администратор (Admin)
- Просмотр статистики системы
- (расширение прав в будущем)

## Функциональные требования

### F1: Аутентификация и авторизация

**F1.1** Система должна поддерживать регистрацию пользователей с указанием роли (customer/contractor).

**F1.2** Система должна поддерживать вход по username/password с выдачей JWT токенов (access + refresh).

**F1.3** Refresh token должен позволять получать новый access token без повторного входа.

**F1.4** Система должна ограничивать доступ к защищённым ресурсам только для авторизованных пользователей.

**F1.5** Система должна разделять права доступа по ролям (только customer может создавать проекты, только contractor может делать ставки).

### F2: Управление проектами

**F2.1** Заказчик может создать проект с указанием: title, description, category, skills, budget, deadline.

**F2.2** Проект должен иметь статусную модель (state machine) с валидными переходами.

**F2.3** Список проектов должен поддерживать фильтрацию по status, category, budget.

**F2.4** Проекты должны поддерживать пагинацию.

**F2.5** Заказчик может отменить проект в статусе CREATED или PENDING_FUNDS.

**F2.6** При отмене проекта недепонированные средства возвращаются на баланс заказчика.

### F3: Ставки (Bidding)

**F3.1** Исполнитель может сделать ставку на проект в статусе CREATED.

**F3.2** Исполнитель не может делать повторные ставки на один проект.

**F3.3** Ставка содержит: cover_letter, proposed_price, proposed_days.

**F3.4** Заказчик может принять одну ставку, остальные автоматически отклоняются.

**F3.5** При принятии ставки создаётся escrow-счёт с суммой предложенной цены.

### F4: Escrow (Условное депонирование)

**F4.1** Средства списываются с баланса заказчика при депонировании.

**F4.2** Средства хранятся в системе до завершения проекта.

**F4.3** При успешном завершении средства переводятся на баланс исполнителя.

**F4.4** При отмене/споре средства могут быть возвращены заказчику.

**F4.5** Система должна автоматически переводить просроченные проекты в статус DISPUTED.

### F5: Выполнение работ

**F5.1** Исполнитель может сдать работу (work_result) при статусе IN_PROGRESS.

**F5.2** После сдачи работы проект переходит в статус REVIEW.

**F5.3** Заказчик может принять работу (переход в COMPLETED, релиз средств).

**F5.4** Заказчик может отклонить работу (переход в IN_PROGRESS или открыть спор).

### F6: Споры (Dispute)

**F6.1** Участник проекта может открыть спор в статусе IN_PROGRESS или REVIEW.

**F6.2** Спор переводит проект в статус DISPUTED.

**F6.3** Только заказчик может разрешить спор (refund или release).

**F6.4** При refund средства возвращаются заказчику.

**F6.5** При release средства переводятся исполнителю.

### F7: Чат

**F7.1** Участники проекта могут обмениваться сообщениями в реальном времени (WebSocket).

**F7.2** Чат доступен для проектов в статусе PENDING_FUNDS, IN_PROGRESS, REVIEW, COMPLETED, DISPUTED.

**F7.3** Сообщения сохраняются в базе данных.

### F8: Отзывы и рейтинг

**F8.1** Участники могут оставить отзыв после завершения проекта.

**F8.2** Отзыв содержит rating (1-5) и optional comment.

**F8.3** Один пользователь может оставить только один отзыв на проект.

**F8.4** Рейтинг пользователя рассчитывается как средневзвешенное по времени (свежие отзывы имеют больший вес).

### F9: Загрузка файлов

**F9.1** Пользователи могут загружать файлы к проектам.

**F9.2** Поддерживаются: png, jpg, gif, pdf, zip, doc, docx, txt, и др.

**F9.3** Файлы сохраняются с UUID именами для безопасности.

**F9.4** Проверка доступа к project_id при загрузке.

### F10: Администрирование

**F10.1** Администратор может получить статистику системы.

**F10.2** Статистика включает: количество пользователей, проектов, активных проектов, сумму в эскроу.

## Non-functional requirements

### NFR1: Безопасность

**NFR1.1** Пароли должны хэшироваться с использованием Werkzeug (pbkdf2:sha256).

**NFR1.2** API должно защищать от SQL injection через ORM.

**NFR1.3** Должен быть реализован rate limiting на критических эндпоинтах.

**NFR1.4** CORS должен быть ограничен списком разрешённых доменов.

**NFR1.5** Секретные ключи должны настраиваться через переменные окружения.

### NFR2: Производительность

**NFR2.1** Страница списка проектов должна загружаться менее 2 секунд.

**NFR2.2** Время отклика API должно быть менее 500ms для типичных запросов.

**NFR2.3** WebSocket должен поддерживать множественные соединения.

### NFR3: Надёжность

**NFR3.1** Система должна сохранять данные в БД после каждой операции.

**NFR3.2** При ошибках должны возвращаться понятные сообщения.

**NFR3.3** Deadline checker должен работать в фоновом режиме.

### NFR4: Удобство

**NFR4.1** Интерфейс должен быть интуитивно понятен.

**NFR4.2** Сообщения об ошибках должны быть информативными.

**NFR4.3** State machine переходы должны быть визуализированы.

## Сценарии использования

### Сценарий 1: Создание и выполнение проекта

```
1. Заказчик регистрируется и пополняет баланс
2. Заказчик создаёт проект (status = CREATED)
3. Исполнитель видит проект и делает ставку
4. Заказчик принимает ставку (status = PENDING_FUNDS)
5. Заказчик депонирует средства (status = IN_PROGRESS)
6. Исполнитель выполняет работу и сдаёт её (status = REVIEW)
7. Заказчик принимает работу (status = COMPLETED)
8. Средства переводятся исполнителю
9. Оба оставляют отзывы
```

### Сценарий 2: Спор

```
1. Проект в статусе IN_PROGRESS или REVIEW
2. Исполнитель сдаёт работу, заказчик недоволен
3. Заказчик открывает спор (status = DISPUTED)
4. Обсуждение в чате
5. Заказчик решает: refund или release
6. Проект завершается с соответствующим переводом
```

### Сценарий 3: Пропущенный дедлайн

```
1. Проект в статусе IN_PROGRESS или REVIEW
2. deadline истекает
3. Background job обнаруживает просрочку
4. Проект автоматически переходит в DISPUTED
5. Участники получают уведомление
```

## State Machine (диаграмма переходов)

```
                    ┌─────────────────┐
                    │     CREATED     │
                    │  (открыт для    │
                    │    ставок)      │
                    └────────┬────────┘
                             │ принятие ставки
                             ▼
                    ┌─────────────────┐
                    │ PENDING_FUNDS   │
                    │ (ожидает оплаты) │
                    └────────┬────────┘
                             │ депонирование
                             ▼
                    ┌─────────────────┐
                    │   IN_PROGRESS   │
                    │   (в работе)     │
                    └────────┬────────┘
                             │ сдача работы
                             ▼
                    ┌─────────────────┐
                    │     REVIEW      │
                    │  (на проверке)  │
                    └────────┬────────┘
                             │
              ┌──────────────┴──────────────┐
              ▼                               ▼
     ┌─────────────────┐            ┌─────────────────┐
     │    COMPLETED    │            │    DISPUTED    │
     │   (завершён)    │            │     (спор)     │
     └─────────────────┘            └────────┬────────┘
                                            │ разрешение
                                            ▼
                                     ┌─────────────────┐
                                     │    COMPLETED    │
                                     └─────────────────┘
```

## Глоссарий

| Термин | Определение |
|--------|--------------|
| Escrow | Условное депонирование - размещение средств у третьей стороны до выполнения обязательств |
| Bid | Ставка исполнителя на проект |
| Project | Заказ на выполнение работы |
| Customer | Заказчик (создаёт проекты) |
| Contractor | Исполнитель (выполняет работы) |
| Dispute | Спор между участниками проекта |
| JWT | JSON Web Token - стандарт для создания токенов доступа |
| WebSocket | Протокол для двусторонней коммуникации |
